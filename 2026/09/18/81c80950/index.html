LLaMA-Factory 实战（三）：单卡后训练全链路——SFT、DPO 与 GRPO/RLVR

系列导航：
（一）数据格式、模板选择与版本调试；
（二）环境搭建、WebUI 训练与模型导出合并；
（三）本篇——用 TRL 在单卡上把 SFT → DPO → GRPO 三条后训练路线完整走一遍。

一、后训练全景：三条路线各自解决什么问题

大模型后训练不是一步到位，而是分工明确的三层：

路线数据形态学什么
SFTprompt + completion「应该怎么回答」
DPOprompt + chosen + rejected「哪个回答更好」
GRPO/RLVRprompt + answer（奖励函数打分）「在可验证的任务上拿高分」

注意 DPO 是直接偏好优化，不是在线强化学习——它把带参考策略约束的偏好目标转化为可监督优化的形式；而 GRPO 需要在线 rollout + 奖励函数，计算量大得多。

本文按 TRL 1.12.x API 编写，模型用 Qwen2.5-0.5B-Instruct 做教学演示（真实项目再换大模型）。所有训练开关默认关闭，先读代码、跑环境诊断，再只打开一个阶段——这是后训练的基本纪律。

二、硬件边界：先算显存账

单卡能跑哪一步，先看这张表（0.5B + 4-bit QLoRA 教学配置的量级估计）：

阶段预计显存单卡建议
SFT4–7 GB16GB 轻松
DPO7–12 GB16GB 可运行
GRPO10–18 GB24GB 更稳妥

数字不是硬件承诺，还受序列长度、batch、生成条数、attention kernel 影响。正确姿势：先用 0.5B + batch_size=1 + max_length≤512 跑通全链路，再扩展模型规模。

训练后的检查点清单（比「跑完」更重要）：

  1. train/loss 整体下降，而不是只看最后一个 batch；
  2. 未见过的题目能否保持输出格式——只背下训练集等于没训；
  3. 是否「只学会格式、没提高正确率」；
  4. adapter 目录里有 adapter_config.json 和权重文件；
  5. 用固定评测集对比 base 与 SFT，不凭几条样例下结论。

四、阶段二：DPO 偏好优化

数据长这样，chosen/rejected 的差异必须反映真实偏好维度（正确性、简洁性、格式），不能只靠长度区分：

关键参数：learning_rate=5e-5（比 SFT 小一个量级）、beta=0.1（约束不偏离参考策略的程度）。

DPO 诊断三看：

  • rewards/margins 应逐步为正，但持续暴涨意味着过拟合；
  • beta 越大越保守，越不容易偏离基座；
  • chosen/rejected 若有明显长度偏差，模型可能学到「越长越好」——这是偏好数据污染的经典信号。

五、阶段三：GRPO + RLVR

GRPO 的核心是组内相对优势：对同一 prompt 采样多条回答（num_generations=4），奖励函数打分，高于组均值的回答概率上升。

GRPO 最大的坑是奖励投机：奖励高但答案差，说明模型找到了验证器的漏洞（比如只输出格式不输出内容）。对策是单独统计 correctness 奖励，别只看总奖励，同时把验证器写严（唯一匹配、严格解析）。

七、常见故障定位表

现象优先排查调整顺序
CUDA OOM序列长度、生成条数、batchbatch=1 → 减长度 → 增累积 → 减 num_generations
bitsandbytes 报错WSL2 驱动、CUDA/PyTorch ABI重建干净环境，跑 python -m bitsandbytes
loss 突然 NaNfp16 溢出、学习率、异常样本bf16 → 降学习率 → 梯度裁剪 → 查 batch
DPO margin 不升数据顺序错、偏好太弱、长度泄漏人工抽查 20 对，再调 beta/lr
GRPO 奖励高但答案差奖励可被投机单独统计 correctness，强化验证器
模型只输出标签SFT 数据过于单一增加推理多样性，保留基座能力数据

最后一条纪律：每次只改一个变量，并保存配置、随机种子、代码版本和评测结果——后训练调试最贵的成本是「不知道上次为什么成功」。

八、小结

SFT 教格式，DPO 教偏好，GRPO 教「在可验证任务上拿分」。单卡跑不动 GRPO 全流程时，DPO + SFT 的组合已经能覆盖大部分场景；等有 24GB 卡再把 GRPO 打开。下一篇回到部署侧，聊聊推理加速与 KV Cache 的优化路线。
