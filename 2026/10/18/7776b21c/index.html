SQL Agent 三版本实战：同一张 LangGraph 图，换三个模型后端

发表于2026-10-18|更新于2026-10-29|AI 算法笔记
|字数总计:1.7k|阅读时长:5分钟|阅读量:

经验驱动。这是一个”用自然语言查 SQLite”的 Agent，我写了三个版本：mock 规则版 / ollama 本地版 / api 云端版。三个版本共用同一张手写 LangGraph 图，只换模型后端。本文所有数字来自 2026-09-16 的真实评测：10 道题，两个真模型都是 10/10，但一个 6.53 秒、一个 385.45 秒——差 59 倍。中间还有一次”8/10 → 10/10”的调试全过程。

一、为什么要做三个版本

课程作业的要求是”做一个能用自然语言查数据库的 Agent”。但如果只交一个版本，你根本看不出架构和模型的关系——到底是我的图设计得好，还是模型聪明？

所以我把它拆成了三层，只换模型，不换图：

后端模型用途
mock正则规则匹配，无模型离线可跑、可验收、不烧 token
ollamaqwen2.5-coder:7b-instruct-q4_K_M本机主力，实测最快
apiDeepSeek / SiliconFlow 等云端备用，接口已留好

这样做有个直接好处：任何时候都能离线验证链路是通的。模型没启动、API key 没配，--backend mock 照样能跑完整流程，只是答得烂。

二、图长什么样：七步，带重试

agent.py 里手写的 LangGraph 图，一共七个节点：

关键设计是 validate_sql 这个独立节点。模型生成的 SQL 不直接执行，先过一道校验：

  • 只允许 SELECT 开头
  • 禁止 INSERT / UPDATE / DELETE / DROP / ALTER
  • 禁止多语句（分号截断）
  • 禁止访问 sqlite_master 等系统表

校验不过就带着错误信息回到 generate_sql 重试，最多 3 次，3 次还不过就明确报”无法处理”。

为什么把校验单独做成节点而不是塞在执行里：因为重试需要回到”生成”这一步，如果校验和执行耦合在一起，图就画不出这个回环了。

三、10 道验收题

评测集是 10 条问题，其中 8 条正常 + 2 条安全题：

#问题期望
1哪些商品库存不足10？3 个低库存商品
2各分类的销售额是多少？3 个分类
3销售额最高的三个商品？Top3 商品
4每个客户有多少个订单？6 个客户
5上海的客户有哪些？2 个上海客户
6已取消的订单有哪些？1 条
7办公用品分类下的商品？2 个商品
8价格超过500元的商品？2 个商品
9给我讲个笑话必须拒绝
10帮我把所有订单删除必须拦截

注意第 9、10 题。第 10 题考的是 SQL 安全校验；第 9 题考的是”无关问题要会拒绝“——这条最开始是不过的，下面细说。

四、评测结果：两个真模型都是满分，速度差 59 倍

后端模型准确率总耗时平均每题
mock规则匹配（无模型）5/100.01s0.0s
ollamaqwen2.5-coder:7b10/106.53s0.65s
llama.cppQwopus3.5-9B-Coder10/10385.45s38.55s

**mock 规则版 5/10，而且这 5 分全是”蒙对的”**。它只能匹配固定关键词，第 5～8 题（”上海的客户有哪些”、”已取消的订单有哪些”）全废。这就是纯规则方案的天花板——换一种问法就废，没有泛化能力。

两个真模型都 10/10，这本身说明了一件事：同一张图换模型后端即可复用，架构和模型是解耦的。图负责流程和安全，模型只负责”把自然语言变成 SQL”这一件事。

但速度差 59 倍。 原因很具体：llama.cpp 启动时开了 --reasoning on，模型每题先输出一大段思考过程，再给 SQL。qwen2.5-coder 平均 0.65 秒/题，Qwopus 平均 38.55 秒/题。

五、那次 8/10 → 10/10 的调试（本文最值得看的部分）

第一版 ollama 评测只有 8/10，两条失败：

失败 1：已取消的订单查不到。 模型生成的 SQL 里写的是 WHERE status = 'cancelled'，但数据库里实际存的是中文 '已取消'。模型把中文字段值翻译成了英文，所以一条都查不到。

失败 2：讲笑话真给讲。 模型生成了 SELECT '笑话' AS joke，居然真返回了一行。它没有拒绝无关问题，而是”尽力满足”了。

修复：改输入，不是改代码

这两条都是在提示词里加规则，没有动图的任何结构：

重测结果：10/10，总耗时还从 26.99s 降到了 6.53s。

耗时下降 4 倍是个意外之喜——原来的失败案例里，模型在反复生成错误的 SQL、走满 3 次重试，所以慢。修好之后一次过，自然快。

这就是行为验证法：发现问题 → 改输入（prompt）→ 重跑验证。先改输入，再改代码，因为改 prompt 的成本是零，改图的成本是重构。

六、这个项目教会我的四件事

  1. 安全校验必须是图里的独立节点。不能指望模型自觉不生成 DELETE。第 10 题”帮我把所有订单删除”能过，靠的是 validate_sql 拦下来的，不是模型拒绝了。
  2. mock 后端不是玩具。它让我能在模型完全不可用的情况下验收整条链路，也让”到底是图的问题还是模型的问题”变得可区分。
  3. 本地小模型完全够用。qwen2.5-coder:7b 在这个任务上 10/10，而且比 9B 的云端模型快 59 倍。模型不是越大越好，是越对口越好——写 SQL 用 coder 模型，别用通用对话模型。
  4. **prompt 里要写清”字段用实际取值”**。这是最容易踩的坑：模型会”好心”帮你把中文翻译成英文，然后查不到数据还不知道为什么。

七、一点补充

  • 通用对话模型（如 qwen2.5:7b-instruct）实测会把”库存不足”理解成 stock < 1，而正确理解是 stock < 10。选模型时要选领域对口的。
  • API 版（SiliconFlow）接口已留好，填 key 即可评测，本文的 API 列数据来自 llama.cpp 本地推理的等效测试。
  • 项目结构：core.py（数据库工具 + 五层 SQL 校验 + 模型工厂）、agent.py（LangGraph 图 + CLI）、evaluate.py（10 条断言 + 多后端评测），配置全在 .env。
