千问3.8-27B模型12G显存适配（二）：把上下文窗口改小，为什么反而不崩了

发表于2026-10-29|更新于2026-10-29|大模型部署与推理
|字数总计:2.5k|阅读时长:8分钟|阅读量:

一、先把结论放前面

最初我把 ZCode 的上下文窗口设成 262,144（26 万），输出上限只有 8,192。结果上下文涨到 13–14 万时就开始报错、模型直接停。

查明白根因是：ZCode 的自动压缩在上下文用掉窗口 85% 时才触发。26 万窗口的 85% 是 22.3 万，而显卡上那块设备 KV 池只有 9.8 万——压缩信号永远飘在墙外，模型每次都在压缩救场之前就撞墙死了。

修法：把窗口压到等于设备 KV 池（9.8 万），压缩阈值落到 8.3 万、稳稳在池内；再按「系统提示 + 工具占 3 万、留 7 万干活」做预算，用到 70–80% 自动压缩、循环复用。12 GB 显卡上跑通了小规模 Agent 任务。

这一篇就是把这个过程完整记下来——因为**”窗口开大反而崩”这件事，反直觉到大部分人第一反应是不信的**。

二、起点：看起来很猛的那套配置

最初在 ZCode 里给 qwen3.8-27b 配的是这样（备份 provider_config.json.bak-20261015-171825 可证）：

参数初值当时想法
contextWindow262,144（26 万）“窗口越大越能装长上下文”
maxOutputTokens.max8,192客户端默认值，没动
reasoningLevel**disabled**（首项即默认）追求极速

注意第三行：这不只是”慢一点”的问题，后面会看到它是能力归零的问题。

还有个当时没意识到的错配：引擎侧其实允许 32768 输出（--default-max-tokens 32768），但客户端上限 8192 比服务端小——等于客户端自己把输出砍掉了四分之三。

三、两个事故，都是日志铁证

事故 A：输出被硬截断

引擎日志里实锤这一行：

拆开看，上下文根本不是问题：

  • prompt 140,790 / 262,144 = 53.7% 用量，还空着 12 万 token；
  • cache 140,736 (100.0%) —— 前缀缓存 100% 命中，性能极好；
  • 但 output 8,192 后面跟着 output limit。

真瓶颈是输出上限：生成到第 8192 个 token 被硬切（finish_reason=length），ZCode 把它包装成 “exceeded the output token maximum”。

那个任务是”读 12 个 HTML 再写一篇长文”，8192 根本不够——它连一半都没写完就被掐了，看起来就像”模型突然不会干活了”。

事故 B：上下文冲爆设备 KV 池

日志里出现过 19 次 这一行：

prompt 从 67,266 一路涨到 94,820，而当时的设备池只有 67,072（旧的 k8v4 配置）。那次失败任务的 prompt 140,790 = 旧池的 2.1 倍。

超池之后会发生什么？走 KVMem 检索。而检索是有损的——作者在自己 README 里实测过 kept=512 / candidates=1397，约 63% 的块被静默丢弃。特征是：

没有错误行、HTTP 200、答案看起来合理但是错的。 严重时才会输出报错、进程停。

这就是口语里说的”上下文到 13 万、14 万左右就报错、模型停止运行”。两个事故，一个在掐输出，一个在穿池，都是”大窗口 + 小保护”这版配置的后遗症。

四、诊断：为什么窗口越大，崩得越早

这一步是整件事的核心，值得单独画出来。

ZCode 有一套自动上下文压缩（compact）机制，逻辑在 @tokenlens 里：

  • 触发阈值 shouldCompact = **0.85 × contextWindow**（源码 args.threshold ?? 0.85）
  • 压缩时把对话压到 targetPercent 0.6（保留 60%）
  • ⚠️ 这跟 DSH 那套 min(0.8×W, W−maxTokens−65536) 完全不是一回事，给 DSH 的 155,648 不能直接照搬到 ZCode

于是关键矛盾出现了：

contextWindow压缩阈值（0.85×W）设备 KV 池结果
262,144222,82298,304❌ 阈值在池的 2.27 倍处 → 上下文涨到 14 万早冲爆池，崩在压缩触发之前
115,00097,75098,304⚠️ 贴着池顶，没有余量，一次长回复就穿
98,30483,55898,304✅ 阈值在池内，留 15% 余量 → 压缩先触发，拦在穿池之前

一句话原理：自动压缩的本意是”快满了就自动瘦身”，但它判断的”满”是按 contextWindow 算的 85%，而真正的硬墙是显存里那块设备 KV 池。你把窗口设成 26 万，等于告诉压缩机制”到 22 万你再瘦身”——可显存里的池才 9.8 万，瘦身信号永远发不出来，模型先撞墙死了。

所以铁律只有一条：

客户端上下文窗口必须 ≤ 设备 KV 池容量。 压缩阈值才落得住，自动压缩才来得及救场。

五、顺手摸出来的「30K / 70K 预算法」

窗口压到 98,304 之后，日常怎么用？给上下文做预算分配：

  • 固定开销 ≈ 30K：系统提示词（含防死循环护栏）+ 工具 schema 描述 + 协议 overhead。这些每轮都在，动不了。
  • 可用空间 ≈ 70K：98,304 扣掉 30K 常驻，剩约 7 万 token 是真正给”对话历史 + 检索资料 + 本次输出”干活的。
  • 压缩在 70–80% 处触发：总上下文用到窗口的 70–80%（约 68K–78K，刚好覆盖 30K 常驻 + 大部分可用区），ZCode 就把旧对话压一遍，腾地方继续干。

这套预算跑通后，模型的行为从”涨到 14 万才崩”变成**”用到七八成自动瘦身、循环复用”——这才是 12 GB 卡能跑 Agent 的真正原因：不是它能一次装下整个任务，而是它能在有限的池里反复腾挪、稳定地干完一个长任务**。

六、修复：具体改了什么

最终落地的 ZCode 配置（C:\Users\tang\.zcode\v2\provider_config.json，条目在 config.modelConfigRules.providerModelRules[]，不是顶层 models——这个结构坑我踩过）：

参数初值（翻车版）终值（跑通版）为什么
contextWindow262,14498,304= 设备 KV 池，压缩阈值 83,558 落池内
maxOutputTokens.max8,19216,384与服务端对齐，长文不再被客户端砍
reasoningLevel 默认档disabled（首项）**low**（提到首项）关思考算术 0/4，开 low 4/4
reasoningLevel 选项含 xhigh去掉 xhigh更慢，长任务易死循环（16 分钟那次就是 xhigh）

引擎侧只动一处保底（桌面 启动方式\启动-终极版-KVMem服务(仅服务)-96k池.bat）：

  • --default-reasoning-effort none → **low**：即使客户端不下发推理档，引擎也走 low；
  • KV 池 98,304 nvfp4 和 --draft-tokens 4 保持不动（draft 8 在散文上反而慢 24%）。

备份链完整保留：bak-20261015-171825（8192 原始版）→ -180500 → -191915 / -192107（最终版）。任何时候都能回退。

七、改完真跑，不是嘴上说说

腾空机器后（GPU 764 MiB / 12,227 MiB、内存空闲 19,977 MB、无超分进程）逐项实测：

项结果
冷启动引擎 6.1 s ready
基线容量KV 98,304 nvfp4｜runtime 3.01 GiB｜free 1.21 GiB
首条性能TTFT 617ms / prefill 1.84k tok/s / decode 165–169 tok/s / MTP 87.6%
推理档数学 none 0/4 → low 4/4；工具调用 low 仍 3/3 全对
边界（池内）prompt 78,772 → 0 次超池告警、中段暗号 100% 取回
边界（越池）prompt 112,015（池 1.14×） → 1 次告警、kept=0 整块被丢、冷预填 180 s
长输出16384 上限下自然产出 **10,926 token，finish=stop**，101.5 s，不绕圈
端到端(17×23)−(128÷4) 答 359 正确（改前 disabled 档答 385）

最关键的是推理档那一行：数学题从 0/4 直接变 4/4，而且工具调用一点没受影响（没有出现”工具调用被写进思考通道”的那种退化）。代价只有每个请求多 0.3–0.9 秒。

八、六条能带走的经验

  1. 区分两种「上限」：contextWindow 是”客户端许诺的上下文大小”，设备 KV 池是”显存里真装得下的 KV”。前者可以随便写大，后者是物理墙。永远让前者 ≤ 后者。
  2. 自动压缩的触发点必须落在硬墙之内：它的阈值按窗口算百分比，窗口设太大阈值就飘到墙外，机制形同虚设。
  3. 客户端上限会盖过服务端：ZCode 的 maxOutputTokens 比引擎 --default-max-tokens 小时，客户端赢。调优必须两端对齐看。
  4. **推理档是”能力开关”不是”速度旋钮”**：关掉思考算术直接归零，开 low 全对且工具不受影响。别为了极速默认关思考。
  5. 显存头号杀手是别的任务：视频超分一开，可用显存从 11 GB 压到 2.5 GB，98K 池直接起不来。跑长任务前先确认后台没吃显存。
  6. 长驻引擎必须手动双击 bat：由 Agent 拉起的进程活不过一轮（外部 Job Object 干净杀掉），这是环境限制不是 bug。

九、能直接照着讲的一段话

「这个 27B 本地部署，引擎侧用了 NInfer + 三元量化 + nvfp4 KV + KVMem 页环 + MTP 投机解码，在 5070Ti 12G 上把显存压到 3 GiB 跑通。

但真正让它能在 ZCode 里干 Agent 活的，是客户端侧的调优：最初我把上下文窗口开到 26 万，结果上下文涨到 14 万就崩——因为 ZCode 的自动压缩按窗口 85% 触发，26 万的 85% 是 22 万，而显存里那块设备 KV 池只有 9.8 万，模型每次都在压缩救场前就冲爆了池。

修法是把窗口压到和设备池一样大（9.8 万），压缩阈值落到 8.3 万、稳稳在池内；再按『系统提示加工具占 3 万、留 7 万干活』做预算，模型用到 70–80% 自动压缩、循环复用，12G 上就能跑通小 Agent 任务。另外把输出上限从 8192 提到 16384、推理档默认开 low（关思考算术直接 0 分），都实测验证过。」
