千问3.8-27B模型12G显存适配（三）：长上下文 Agent 调优方法总览

发表于2026-10-29|更新于2026-10-29|大模型部署与推理
|字数总计:2.8k|阅读时长:9分钟|阅读量:

前两篇分别是「这东西是什么」和「我怎么调崩又调回来」。这一篇是方法总览——把 12 GB 的账、四个杠杆、五个绕不过去的问题压成一页，别人问起能顺着讲下来。

一、一分钟讲完这套东西

我要在 RTX 5070 Ti Laptop 12 GB 上跑 Qwen3.8-27B 本地 Agent。27B 的原生权重 + KV 远超 12 GB，所以没用通用引擎，而是选了为 sm_120a 架构专编的 NInfer，叠加三元量化（权重压到 ~8.9 GB）+ nvfp4 KV 量化 + KVMem 页环（历史 KV 放内存、按需搬显存）+ MTP 投机解码，把设备侧压到约 3 GiB。

长上下文的关键不是把窗口开大，而是让窗口小于等于设备 KV 池——因为超出池之后 KVMem 的检索是有损的，会静默丢块。我把窗口定在 98,304、池也定在 98,304，压缩阈值落在池内，12 GB 上才跑得通小 Agent 任务。

实测：设备池 3.01 GiB、prefill 1.84k tok/s、decode 165–169 tok/s、MTP 接受率 87.6%、冷启动 6.1 s。

这就是完整骨架。下面把每一句拆成能查的东西。

二、12 GB 的账：四个杠杆怎么合力

三、五个绕不过去的问题

Q1：12 GB 怎么跑得动 27B？

四笔账：

  1. 权重：三元量化把 27B 压到 ~8.9 GB；
  2. KV：nvfp4 量化，页大小 64 token，设备池只占 ~3 GiB（runtime 3.01 GiB）；
  3. 历史：超出池的部分放 Host RAM（~7 GiB），按相关性检索回显存——所以”逻辑上下文 256K”≠”显存里塞 256K”；
  4. 速度：MTP 投机解码把 decode 再拉一截。

一句话：权重靠量化，KV 靠量化 + 分层，长上下文靠”内存换显存”。

Q2：TTFT 6 s → 0.4 s 是怎么回事？

这是两笔账，必须分清，否则听起来像逻辑漏洞：

  • 6.1 s = 引擎冷启动（加载权重 + 捕获 CUDA Graph），一次性开销，跟请求无关；
  • 0.4 s 量级 = 前缀缓存续接后的 warm TTFT：系统提示 + 工具表 + 历史前缀被复用，只 prefill 新增部分。

上游有更极端的同构数据：同会话长前缀复用，第二轮 TTFT 70,829 ms → 126.5 ms（cache 命中 80,075 token）。

还有那个常被引用的 **”99.8% 命中率”**，口径要说准：它来自上游 benchmarks/evidence/ 的 58,330 / 58,459 token 复用 = 99.78%，指的是续接请求里复用历史 token 的比例，不是泛化命中率，更不能和”6 s→0.4 s”混成一句说。

Q3：为什么 decode 是 memory-bound？

每生成 1 个 token，都要把全部权重（8.9 GB）+ 全部活跃 KV 从显存读一遍。算力几乎闲着，瓶颈是显存带宽。

推论很重要：**量化直接砍的是”每个 token 要读多少字节”**，所以量化对 decode 的提速是乘性的——这也是三元量化不只是”省显存”，还真的”变快”的原因。

一个很好的类比：跑分图常给你看 prefill（几百上千 tok/s，好看），日常等你的其实是 decode（几十到一百多 tok/s）。上游的 V100 例子就很典型：prefill 2000 t/s vs decode 236 t/s，差近十倍。

Q4：MTP 投机解码的原理？

  1. 草拟：MTP 草稿头先预测后 N 个 token（N = --draft-tokens）；
  2. 验证：主模型一次并行前向把这 N 个一起验证；
  3. 接受 / 重采样：连续接受的前缀直接采用；第一个分歧点重采样，后面丢弃；
  4. 收益：一次前向产出多个 token。接受率越高越赚。

本机实测接受率 **87.6%**。但注意 --draft-tokens 不是越大越好：

文本类型draft 4draft 8
数数字（高度可预测）169.0 tok/s148.2 tok/s
散文（不可预测）69.6 tok/s52.7 tok/s（**慢 24%**）

草稿越深，在不可预测文本上亏得越多——因为多出来的草稿几乎全被拒，白算。所以 draft 4 是最优，不动。

Q5：这套东西有什么问题？

这是最值得讲的部分，因为问题都是实测出来的，不是猜的：

  1. 关思考算术 0/4，开 low 4/4。模型默认”不想”，reasoning=none 时算术 3–4 个 token 直接吐答案，错得很干脆（不是想错，是没想）。开 low 立刻 4/4，且工具调用仍 3/3 全对。
  2. 超池静默丢块（下节详述，这是最硬的一条）。
  3. 客户端上限会盖过服务端：ZCode 的 maxOutputTokens 8192 把长文硬切（finish_reason=length），跟引擎无关。
  4. 显存头号杀手是别的任务：视频超分一跑，可用显存从 11 GB 压到 ~2.5 GiB，98K 池直接起不来。

四、最硬的一条发现：超池就静默丢块

这条之所以硬，是因为它在作者 README 里有逐字记录，不是我的主观判断：

  • 「题面 token > 池 token ⇒ 单请求答案不可信」（引擎打 unverified 告警）
  • 「超池 + 检索未开时，失败形态是『静默错』（HTTP 200、答案貌似合理而非报错）」
  • 2026-10-07 实测：超池臂检索关 ⇒ turn1 命中 0/6、静默错 6/6；检索开（8192）⇒ 6/6 命中；不过池的两态都 2/2。
  • 源码硬约束：**host_pages + pool_pages ≥ logical_pages，否则启动即拒**（startup.cpp:1806-1840）

我自己的实测与它完全同构：

prompt token相对池超池告警中段暗号冷预填耗时
21,5170.22×0取回 ✅15 s
57,2890.58×0取回 ✅63 s
68,0470.69×0取回 ✅84 s
78,7720.80×0取回 ✅104 s
112,0151.14×1 次侥幸取回180 s

越池那次日志里出现 kept=0 / candidates=1648——整块被丢。暗号这次侥幸没落在被丢的块里，所以”取回成功”了；换个位置就是静默错误。

这说明什么：这不是 bug，是设计边界。所以正确做法不是”想办法让它超池也别丢”，而是根本不要超池。这也是上一篇把窗口从 26 万压到 9.8 万的依据。

五、为什么池不直接开大？

有人会问：既然池越大越安全，为什么不把 --kv-capacity 开到 20 万？

因为池是显存里的页数。12 GB 里权重已经占了 8.9 GB，剩下 3 GB 出头刚好装 98,304 token（free 1.21 GiB，已经没什么余量了）。再往上开，引擎直接报”显存不够”起不来。

所以这里没有”更好的解”，只有在给定显存里选一个不越界的最大池，然后让所有上层配置服从它。这就是整套方法的中心思想：

显存 → 定池；池 → 定窗口；窗口 → 定压缩阈值；阈值 → 定你的任务能多长。

六、六条可迁移的方法论

  1. **区分”许诺的上限”和”物理的上限”**。contextWindow 是许诺，设备 KV 池是物理。永远让许诺 ≤ 物理。
  2. 自动压缩的触发点必须落在物理墙内。按百分比算阈值的机制，窗口设太大就整体失效。
  3. 客户端上限会盖过服务端上限。两端必须对齐看，否则你以为在调引擎，其实在被客户端截断。
  4. 推理档是能力开关，不是速度旋钮。关掉思考，某些能力直接归零而不是”略降”。
  5. 先测边界，再定配置。所有”应该够用”的判断都要用超池实验证伪一次。
  6. **单卡小显存的第一原则是”别贪”**。显存贴边运行时，任何”再多一点”都是崩溃。

三篇连起来看：千问3.8-27B模型12G显存适配（一）：引擎、模型与参数在讲什么 讲这套系统由什么构成、每个参数在管什么；千问3.8-27B模型12G显存适配（二）：把上下文窗口改小，为什么反而不崩了 讲我怎么在客户端把它调到不崩；这一篇讲把这些经验抽成方法后的样子。如果你也在一张 12 GB 的卡上折腾 27B，希望这三篇能让你少踩两个坑——尤其是那个不报错、只给错答案的坑。
