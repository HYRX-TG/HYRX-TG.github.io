做运维 / SRE 久了，有三个痛点一直绕不开：

1. **大厂的 AIOps 工作流是藏起来的。** 你在外面基本拿不到阿里、腾讯、字节生产级的 Dify 工作流或 StackStorm 编排——那是人家的核心资产。
2. **学习资料是散的。** 知识散在几百篇博客、文档、视频里，没有一条"从原理到生产"的连贯路线。
3. **告警处置还是靠人。** 告警来了，人去翻 dashboard、猜根因、手敲修复命令。

我这个项目的核心想法很简单：**把"学"和"练"做成两套互补的系统**——一套给你看知识（知识图谱），一套给你真跑闭环（AIOps 引擎），再用一套动手实验把两者串起来。

## 一、这个项目到底是什么

一句话：**一个可交互的 SRE / DevOps 知识图谱网站 + 一个自研的 AIOps 研判引擎，外加一套能在你自己虚拟机里跑的故障注入实验。**

```
┌─────────────────────────┐           ┌──────────────────────────────┐
│  3000 知识图谱（前端）     │           │  8600 AIOps 引擎（后端）       │
│  Next.js + React         │   弱耦合   │  FastAPI                     │
│  13 主题区 / 300 节点     │ ────────▶ │  告警 → 分级 → 研判 → 审批      │
│  中英双语 / 深浅色        │  AI 面板   │  + vm-agent 节点侧执行          │
│  纯学习资料，静态站       │  告警染色   │  真实跑的闭环                  │
└─────────────────────────┘           └──────────────────────────────┘
            │                                        ▲
            │                                        │
      你读它学原理                      vm_probe.py 把虚拟机故障
                                     翻译成告警上报 ← 你的虚拟机
```

两个系统**解耦**：知识图谱是静态学习资料，引擎是真实跑的；它们之间只通过"AI 面板 + 告警染色"弱耦合，各自都能独立运行。这点很重要——后面架构篇会展开。

## 二、你在这个项目里能收获什么

- **对别人**：一份能直接看、能点、能搜的 SRE 知识地图（300 个节点，从装 Linux 到上生产）；一套把"告警 → 诊断 → 建议 → 审批"讲透的引擎拆解。
- **对自己**：一份能回看的笔记。我后面要做的本地蒸馏、面试准备，这套东西就是我的"智能运维"底座和面试亮点素材。
