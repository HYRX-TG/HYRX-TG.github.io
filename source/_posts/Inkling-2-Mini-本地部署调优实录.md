## 一、先说清楚这是个什么模型，为什么值得折腾

Inkling 2 Mini 是 Thinking Machines Lab（Mira Murati 离开 OpenAI 后创立的公司）2026 年 11 月 20 日发布的模型，Apache 2.0 开源。它的架构很有意思——**26.4B 总参数，但每生成一个 token 只激活 3.4B**，是个"循环稀疏 MoE"：24 层里养着一堆专家，每次只叫 8 个干活，中间还有 13 层要重复跑 3 遍。

官方吹的卖点是"小到能塞进笔记本"。我手上这台机器是 **RTX 5070 Ti Laptop，12GB 显存 + 31GB 内存**，正好是想验证这句话的那类设备。

下载的时候特意选了无审查版的 Q4_K 量化（15.39GB），想着监督微调 + 2.2T token 强化学习出来的模型，写代码和 Agent 应该不差。结果一上手就发现问题——**这玩意儿慢得让人怀疑人生**。

这篇文章就是把从 13 tok/s 折腾到 50 tok/s 的全过程，以及中间踩的坑、挖出的免费提速点，完整记下来。不讲空话，全是实测。

## 二、第一个认知坑：3.4B 激活 ≠ 只要 3.4B 的显存

很多人（包括一开始的我）会想：既然每次只激活 3.4B 参数，那显存占用应该不大吧？大错特错。

这里要分清**三笔账**：

| 账 | 管什么 | 这个模型的情况 |
|---|---|---|
| 算力账 | 快不快 | 每次只算 3.4B，省算力 |
| 驻留账 | 装不装得下 | 全部专家必须随时在场，15.39GB |
| 搬运账 | 实际有多慢 | 专家放内存就得跨 PCIe 搬，慢 |

为什么专家必须全在场？因为**下一个 token 该选哪 8 个专家，事先不知道**——输入不同，选的专家就不同，所以 128 个专家一个都不能删。打个比方：餐厅有 128 个厨师，每次来客只点 8 个厨师的菜，但你不知道客人点什么，128 个都得在岗站着。

这个模型的专家占了总权重的约 90%（24 层 × 每层约 575MB ≈ 13.8GB）。我的 12GB 卡连一层专家都放不下，所以默认配置 `--n-cpu-moe 24` 把**全部 24 层专家都扔进内存**了。每生成一个字，都要跑一趟内存去取权重——被内存带宽卡死。

**13 tok/s 不是参数没调好，是硬件天花板。** 想提速只有一条路：让权重进显存。

## 三、第一次提速：线程 8→16，接近翻倍（但这是小招）

第一反应是调 CPU 线程数。既然专家在内存里靠 CPU 读，那线程多了应该读得快。

实测（同一段长 prompt，各跑两次）：

| | prefill（读题） | decode（出字） |
|---|---|---|
| 线程 8 | 38.4 / 15.8 tok/s | 7.9 / 8.0 tok/s |
| 线程 16 | 36.5 / 19.2 tok/s | **13.2 / 13.5 tok/s** |

出字速度接近翻倍，读题速度没变——符合预期。这是个零成本的小招，但天花板明显，13 tok/s 还是慢。

**踩坑记录**：我写的启动脚本里带了中文注释，Windows 的 cmd 按 GBK 解码 UTF-8 中文，把中文拆成乱码片段，其中一些字节被当成命令分隔符，把 `echo`、`http:` 拦腰截断成 `cho`、`ttp:` 去执行，满屏"不是内部或外部命令"。**本机 bat 脚本的铁律：一律纯英文（ASCII）**，重写后 nonASCII=0，问题解决。

## 四、真正的解法：换 2bit 量化，让专家全进显存

既然瓶颈是专家在内存，那就换一个能整份塞进 12GB 的量化。IQ2_M 是 8.67GB，专家可以全部进显存。

下载走 hf-mirror 直连（不用代理），实测峰值 100MB/s，1 分 45 秒下完，文件 8,665,091,680 字节校验通过。

启动参数的关键变化：`--n-cpu-moe 24 → 0`（一层都不卸载，专家全进显存），GPU 占用 11.5GB。

实测结果：

| | Q4_K（线程16） | IQ2_M |
|---|---|---|
| 出字速度 | 13 tok/s | **56-60 tok/s** |
| 模型大小 | 15.39GB | 8.07GB |
| 专家放哪 | 全在内存 | 全在显存 |
| 每字耗时 | ~75 毫秒 | ~17 毫秒 |

**翻了 4.3 倍。** 这就是把书从隔壁房间搬回桌上的效果——省掉了每字几十趟的跨房间搬运，剩下就是纯算力。

**又踩一坑**：测速时 PowerShell 构造含中文的 JSON 请求会返回 400，换成 curl + `--data-binary @file` + 英文 prompt 就正常。另外 `max_tokens` 给太小（比如 128）时，思考会吃光预算导致答案返回空字符串——这个模型是思考型的，必须 `max_tokens>=512` 配 `reasoning_budget=512`。

## 五、上下文窗口的拉锯：不是越大越好

IQ2_M 全塞显存虽然快，但显存几乎被吃满，留给 KV 缓存（对话的"草稿纸"）的空间很小，上下文只能开 32K。而 ZCode 这些客户端动不动就报"窗口不够"。

所以我实测了多组"上下文大小 × 卸载专家层数"的组合，找平衡点：

| 窗口 | 卸载层数 | 速度 | 显存余量 | 结论 |
|---|---|---|---|---|
| 32K | 0 | 57 tok/s | 432MB | 窗口太小，客户端报错 |
| 64K | 8 | 40 tok/s | 1.2GB | 可用 |
| **96K** | **8** | **32 tok/s** | **1.1GB** | 最终默认 |
| 128K | 12 | 27 tok/s | 164MB | 一长对话就崩 |

核心思路：**不用把所有专家塞显存**。把少部分专家挤到内存，腾出显存给 KV 缓存，窗口就能开大。代价是那几层走 PCIe，但只卸几层的话速度损失有限。最终定在 96K + 卸 8 层。

## 六、挖到的免费午餐：KV 缓存从 q8 改 q4，纯赚

这是之前一直没试的杠杆。KV 缓存（对话的"草稿纸"）也能量化压缩。

| | 显存余量 | 速度 | 5.5 万字长对话 |
|---|---|---|---|
| KV=q8_0 | 1.6GB | 33 tok/s | 能跑 |
| **KV=q4_0** | **2.2GB** | **32 tok/s** | 能跑 |

**省了 568MB 显存，速度几乎没掉。** 打个比方：对话越长草稿纸越厚，把草稿纸上的字写小一半（q4），桌子就多出一大块空间，而写字速度不变。这是白捡的便宜，直接设为默认。

配合这个优化，我用一份真实的 42 轮长对话（系统提示 + 20 轮问答 + 追问，约 5.5 万 token ≈ 40 万汉字）压测，96K 配置稳稳跑完，显存余 1GB。

## 七、长对话的真相：首轮 130 秒，追问 1 秒

看后台日志发现一个有趣的现象。同一段长对话：

- 第一次提问：读题 34,212 token 花了 **129.7 秒**，出字 210 token 花了 5.7 秒——**97% 的时间在读题**。
- 第二次追问：读题只用了 **1,045 毫秒 / 112 token**，总时间 4.3 秒。

秘密藏在日志的 `LCP similarity` 那一行：`f_sim_best = 0.997`。LCP 是最长公共前缀——服务器发现这次的问题和上次有 99.7% 内容一模一样（就是那些重复的对话历史），直接把上次算好的结果复用，不重算了。

**所以长对话能实用的关键，不是模型记性好，是服务器把上次算的账本留着没扔。** 前提是前缀一模一样——在 ZCode 里只要在同一会话连续对话，缓存一直命中；中途换模型、清历史、改系统提示词，前缀变了，就要重新等 2 分钟。

## 八、三十几 K 的 token 是被谁吃掉的？

顺着长对话继续挖：为什么直接 curl 本地端口时，上下文从 0 开始；一进 ZCode 就吃掉三十几 K？

从 ZCode 的真实请求记录里挖出来逐段数 token：

| 部分 | token 数 | 占比 |
|---|---|---|
| **工具定义（56 个）** | **25,338** | **71%** |
| 对话历史（7 轮） | 8,529 | 24% |
| 系统提示词 | 1,315 | 4% |

真相是：**七成不是对话历史，是 56 个工具的说明书被整份塞了进去**。其中 20 个是 MCP 插件工具（documents/pdf/presentations/spreadsheets 四个插件，每个带 get_view/open/read/search/show 五件套），不管你用不用，每次都全塞。

要纠正一个常见误解：这不是"让模型学会用工具"——模型本来就懂 function calling，不需要教。这 129 秒只是在逐字念那 8.5 万字符的工具说明书，念一遍才知道"哦，我有这些工具可以调"。它不理解、不记忆，每次重新念——所以才叫 prefill（预填充）。

好在工具清单在最前面且永远不变，从第 2 轮起被 LCP 缓存命中，那 25,338 token 就不用重读了。所以首轮那 130 秒只在开会话时付一次。

针对这个，ZCode 提供了 `toolSearchMode`（可选 `off`/`local`/`auto`，默认 `off`）。改成 `local` 就是真正的按需加载：先只给模型一份工具目录，用到哪个它自己搜索、自动加载完整说明书。省约 2 万 token，用到的工具自动回来，随时改回 `off` 即全量恢复，完全可逆。代价是调用工具时多一次往返。

## 九、参数速查表（96K 最终配置）

| 参数 | 值 | 人话解释 |
|---|---|---|
| `-c` | 98304 | 上下文窗口，96K |
| `-ngl` | 99 | 层数全交给显卡 |
| `-np` | 1 | 只开 1 个并发槽，开 4 个显存乘 4 直接爆 |
| `--n-cpu-moe` | 8 | 卸 8 层专家到内存，换 KV 空间 |
| `-ctk/-ctv` | q4_0 | KV 缓存压成 4bit，省 568MB |
| `-ub/-b` | 128/512 | 计算批次，512 会溢出约 3GB |
| `--threads` | 16 | CPU 线程数 |
| `--reasoning-budget` | 512 | 限制思考长度，不设会返回空答案 |

改完必须重启服务才生效。想再调：命令行直接带参数，`run-iq2m-flex.bat 131072 12` 这种，不用改文件。

## 十、几点老实话

1. **速度翻倍的代价是质量**：2bit 量化在写代码、多步推理上会悄悄出错——这个我专门做了十项实测，另开一篇讲。
2. **我启动的服务进程活不过当前对话轮次**（这个环境的限制），所以测速时必须把"启动+等待+测速"放同一操作里。日常用还是自己双击启动脚本最稳。
3. **权衡的本质**：窗口越大，得分给 KV 缓存让路，就得卸更多专家进内存，速度就往下掉。96K 是这张卡上"能干活又不卡"的甜点。

从 13 tok/s 到 50 tok/s，中间没有魔法，就是一笔一笔算显存账、一个一个试杠杆。最值钱的两个发现——KV 从 q8 改 q4、LCP 前缀缓存——都不是调参调出来的，是看日志、读请求体挖出来的。**能实测就别猜，日志里藏着答案。**
