## 一、这台机器在跑什么

机器是 RTX 5070 Ti Laptop：**12 GB GDDR7 显存 + 31.2 GB 内存**，Win11。

上面跑的东西不是"能聊天的本地模型"，而是一个**能接客户端、会调工具的本地 Agent 后端**：

- 对外暴露 **OpenAI 兼容接口**（`/v1/chat/completions`，端口 8096），所以 ZCode、DSH、任何 OpenAI SDK 客户端都能直接接；
- 模型是 **Qwen3.8-27B**，三元量化后权重约 8.9 GB；
- 长上下文靠 **KVMem 页环**（历史 KV 放内存、按需搬显存），不是靠把窗口开大；
- 一次只服务一个会话（`--max-concurrency 1`），设计上就是"我的私人助理"而不是"给团队用的服务"。

一句话：**用一张 12 GB 的消费级显卡，跑一个 27B 的、能干活的长上下文 Agent。**

## 二、一条请求走过四层

理解这套东西，先看请求怎么流：

![一条请求走过的四层](/images/ninfer-27b-arch.png)

| 层 | 是什么 | 关键点 |
|---|---|---|
| 客户端 | ZCode / DSH / curl | 只认 OpenAI 协议，跟引擎解耦 |
| 引擎 | `ninfer-serve-120a.exe`（:8096） | 管 KV、管采样、管投机解码，是全部调优的落点 |
| 模型 | `.ninfer` v3 制品 | 不是 GGUF、不是 safetensors，专属格式 |
| 存储 | 显存（权重 + 设备 KV 池）+ 内存（Host KV） | 长短上下文的真正分界线在这一层 |

**这四层是解耦的**，所以调优可以分头做：引擎侧改显存/KV 怎么摆（第一篇的参数表），客户端侧改窗口和输出上限怎么许诺（第二篇的实录）。两边任何一个没对齐，都会以"看起来像模型变傻"的方式失败。

## 三、为什么是这个引擎

### 一张卡锁死一个二进制

NInfer 是**按 GPU 架构分发**的：一个架构一个二进制，**没有回退机制**。选错了不是"性能差一点"，是直接起不来。

| 架构 | 对应显卡 | 引擎包 |
|---|---|---|
| sm_86 | 30 系 | `infer-engine-sm86` |
| sm_89 | 40 系 | `infer-engine-sm89` |
| **sm_120** | **50 系（Blackwell）** | **`infer-engine-sm120a`** |

5070 Ti 是 sm_120（compute capability 12.0），所以必须用 `sm120a` 那套。sm_120a 的 exe 里**不带 sm_89 的 PTX**，反之亦然——这也是为什么不能拿"通用引擎"的思路去套它。

顺带三个前置坑，都是"不报错但就是不工作"的类型：

- `.ninfer` 制品必须是 **v3**，v2 不通用；
- **所有路径必须纯 ASCII**，中文路径报 `invalid UTF-8 byte`；
- 若干开关**只能以环境变量形式设置**，写配置文件无效，且少一个不会明确报错。

（部署细节我在另一篇 [12G 显存跑 27B：NInfer + KVMem 本地部署实战](/2026/05/12/cd37c220/) 里写过，这里不重复。）

### 为什么不是 vLLM / llama.cpp / ollama

这是面试和评论区最常被问的一句。诚实的答案是：**这是架构取舍，不是盲目选型。**

- **vLLM**：面向吞吐和多并发，启动就要几百秒，12 GB 卡上跑 27B 的长上下文不是它的目标场景；
- **llama.cpp / ollama**：稳、生态好，但长上下文能力路线不同，吃不下这套页环；
- **NInfer**：原版只认 sm_120a、只吃 `.ninfer`、**没有连续批处理和多卡**——牺牲通用性，换来的正是 **KVMem 长上下文环**。

说白了：我需要的不是"通用推理服务"，是"在一张 12 GB 卡上把 27B 的长上下文塞进去"。只有这条路走通。

## 四、引擎的四个杠杆

所谓优化，**不是改模型权重**，而是把下面四个杠杆按硬限制拧紧。

| 杠杆 | 作用 | 本机取值 | 效果 |
|---|---|---|---|
| **三元量化**（GSQ-RCO IQ3_XXS） | 权重从 bf16 的 ~54 GB 压到 ~8.9 GB | 8.9 GB | 27B 塞进 12 GB 还留出 KV 池 |
| **nvfp4 KV 量化** | 每个 KV 元素 4 bit | `--kv-dtype nvfp4` | 同显存约装 **2× token**（相对 k8v4/bf16） |
| **KVMem 页环** | KV 拆成"设备池（显存，小）+ 主机池（内存，大）"，按相关性搬页 | 池 98,304 token / Host 7 GB | 逻辑上下文可远超显存容量 |
| **MTP 投机解码** | 草稿头先草拟 N 个 token，主模型一次并行验证 | `--draft-tokens 4` | decode 提速，接受率实测 87.6% |

四个杠杆合起来的账（12 GB 怎么装下 27B）：

```
27B bf16 权重       ≈ 54 GB   ← 一张卡根本放不下
三元量化后权重      ≈  8.9 GB
设备 KV 池(98,304)  ≈  3.01 GiB
                    ─────────
显存合计            ≈ 11.9 GB / 12 GB   ← 刚好贴边
Host KV（内存侧）    ≈  7 GB
```

**这解释了所有后续调优的动机**：显存已经贴边了，任何"再多放一点"的念头（窗口开大、并发开多、池开大）都会直接换来崩溃。所有参数的意义，都是在这个 11.9 / 12 的夹缝里做取舍。

## 五、这个模型能干什么、不能干什么

这是最该先搞清楚的部分——**它的短板不是"稍微差一点"，而是断崖式的**。

### 擅长

- **中文表达与改写**：长文、公文、技术文档，语感相当稳；
- **结构化输出**：JSON/表格/固定模板，`temperature 0.2` 下几乎不会破坏格式；
- **工具调用**：函数名、参数、enum 选择都准（实测 3/3 全对），这是它能当 Agent 的前提；
- **按格式听话**：给它 schema 它就照着填，不需要反复纠正。

### 短板（每一条都实测过）

| 短板 | 实测表现 | 应对 |
|---|---|---|
| **不思考就算错** | 推理档 `none` 时数学 **0/4**（忘打折、算错乘法），`low` 起 **4/4** | 默认档必须开 `low` |
| **事实性会编** | 法条、API 签名、版本号会一本正经地胡说 | 必须外部核实，别信它的"记忆" |
| **超池静默丢召回** | prompt 超过设备 KV 池后，中段 55–63% 块被丢，**无报错、HTTP 200、答案看似合理但是错的** | 窗口必须 ≤ 池（第二篇整篇讲这个） |
| **只能单会话** | `--max-concurrency 1`，多并发每槽吃显存且单流掉速 | 一次只跑一个任务 |

第三行是这套系统里最危险的一条：**它不报错**。你不会收到异常，只会收到一个"看起来很合理但错了"的答案。

### 所以它适合什么

- ✅ 私人长文助手（写作、改写、总结、翻译）
- ✅ 小规模 Agent 任务（读文件、改配置、按流程跑工具链）
- ✅ 代码理解与局部改写（不需要跑起来验证的那种）
- ❌ 精确算术、财务计算（除非确认思考档开着，且仍要复核）
- ❌ 事实问答、法条引用、API 文档（必须外部核实）
- ❌ 高并发 / 多用户服务
- ❌ 一次吃 20 万 token 的整库分析（会静默丢块）

## 六、参数逐条含义

这是本篇的重点。**每个参数都在管一件具体的事，改错的后果也很具体。**

### A. 显存与 KV（最要命的一组）

| 参数 | 管什么 | 本机取值 | 改错的后果 |
|---|---|---|---|
| `--kv-capacity` | **设备 KV 池**：显存放在显存里的 KV 页数（页大小 64 token） | `98304` | 调大 → 显存不够起不来；调小 → 更容易穿池丢块 |
| `NINFER_KV_WINDOW` | 引擎内部的逻辑窗口，**必须与池对齐** | `98304` | 与池不一致会让压缩/检索判断错位 |
| `--kv-dtype` | KV 的量化格式 | `nvfp4` | 换成 `k8v4` 同显存只能装一半；`rk4v4` 在 cc12.0 上直接被拒 |
| Host KV 上限 | 内存侧能兜多少历史 KV | `~7 GB` | 太小 → 检索无从检索；太大 → 挤爆 31 GB 内存 |
| `--max-context` | **逻辑**上下文上限（可以喊很大） | 由客户端窗口决定 | 只改它不改池 = 主动开启静默丢块 |

> **必须记住的一句**：`--max-context` 是"我许诺能装这么多"，`--kv-capacity` 是"显存里真的放得下这么多"。前者随便写，后者是物理墙。**窗口必须 ≤ 池**。

### B. 生成与输出

| 参数 | 管什么 | 本机取值 | 说明 |
|---|---|---|---|
| `--default-max-tokens` | 服务端默认单次输出上限 | `32768` | **客户端上限比它小时，客户端赢**（真实踩坑点） |
| `--draft-tokens` | MTP 草稿深度 | `4` | 4 最优；8 在散文上**慢 24%**（可预测文本才适合加深） |
| `temperature` | 随机度 | `0.2` | 偏收敛，Agent 场景要稳不要花 |
| `top-p` |  nucleus 采样 | `0.8` | 比默认 0.9 更聚焦 |
| `presence_penalty` | 抑制重复 | `0.05` | 略正，防绕圈复读 |

采样这三个数（`0.2 / 0.8 / 0.05`）是 Agent 场景的手感值，不是理论最优：要的是"同一个输入别给我三个答案"，同时别退化成复读机。

### C. 思考档（能力开关，不是速度旋钮）

| 参数 | 管什么 | 本机取值 |
|---|---|---|
| `--default-reasoning-effort` | 引擎侧保底推理档 | `low` |
| 客户端 `reasoningLevel` | 客户端下发档位，覆盖引擎保底 | `["low","medium","disabled"]`（首项即默认） |

实测四档：

| 档位 | 数学 | 工具调用 | 相对耗时 |
|---|---|---|---|
| `none` | **0/4** | 3/3 | 最快 |
| **`low`** | **4/4** | **3/3** | +0.3～0.9 s/请求 |
| `medium` | 4/4 | 3/3 | 更慢 |
| `high` | 4/4 | 3/3 | 明显更慢 |

**`low` 是唯一性价比点**：数学从 0 变满分，工具调用毫发无伤，代价半秒。`xhigh` 那档更慢而且长任务容易死循环，已经去掉了。

### D. 稳定性与并发

| 参数 | 管什么 | 本机取值 | 说明 |
|---|---|---|---|
| `--recover-invariant-failures` | 内部不变量失败时尝试恢复而不是杀进程 | 开 | 一个坏请求不该让整个引擎死掉 |
| `--max-concurrency` | 并发槽位数 | `1` | 每多一槽都吃显存，且单流 decode 掉速 |

## 七、出处与边界（必须说清楚）

这套东西**不是我写的引擎**。出处链条：

| 层 | 项目 | 说明 |
|---|---|---|
| 基础引擎 | `Neroued/ninfer` | NInfer 本体 |
| 3090 适配 fork | `ashalliants/ninfer-3090` 等 | 0.11.0-rtx3090 基线 |
| 通用 KVMem | `kvmem/kvmem` | 分层 KV：GPU / Host RAM / 可选 SSD |
| KVMem 页环 | `tancau/ninfer-kvmem-ring` | 环 + 检索的移植面 |
| **融合发行版** | **`1314521gjy/ninfer-fusion-kvmem`** | **我用的这套的真正源头，Apache-2.0** |

我做的事情是：**在 5070 Ti 上完成部署、参数调优、以及逐条实测验收**——包括测出超池静默丢块的边界，并把客户端窗口钉回池内。

商用提醒：引擎是 Apache-2.0，但**模型权重另有许可**（部分衍生适用 Swift Open License，含商业收入门槛），不能把整体当 Apache-2.0 用。

## 八、小结

- 引擎是**一架构一二进制**的 NInfer，选错直接死；
- 27B 能上 12 GB，靠的是**三元量化压权重 + nvfp4 压 KV + KVMem 页环借内存 + MTP 提 decode**；
- 显存账是 **11.9 / 12 GB**，贴边运行，所以参数上没有"随便调调"的余地；
- 这个模型的短板是**断崖式**的（不算就错、会编、超池静默丢块），参数配置的第一目标不是"更快"，而是**别掉进这些断崖**。
