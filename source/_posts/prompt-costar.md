> 经验驱动。CO-STAR 是我最常用的提示词框架，把"上下文/目标/风格/语气/受众/响应"一次写清。本文附上我本机用 `qwen2.5-0.5b-instruct` 真跑过的完整案例和真实输出。

## CO-STAR 是什么

六个字母对应六个要素：

- **C — Context（上下文）**：背景、前置信息。
- **O — Objective（目标）**：这次具体要完成什么。
- **S — Style（风格）**：模仿谁、什么文风。
- **T — Tone（语气）**：正式 / 轻松 / 自信 / 克制。
- **A — Audience（受众）**：写给谁看。
- **R — Response（响应）**：输出格式、长度、禁忌。

它和上一篇"方法论"的关系：方法论是原则，CO-STAR 是把原则落到纸面的固定模板。

## 真跑案例：给 DevNote 写推广文案

我本机用 0.5B 模型跑过这条完整提示词：

```
# 用 CO-STAR 写的提示词
C（背景）: 我们是一款面向程序员的云笔记工具，叫 DevNote。
O（目标）: 写一条 60 字以内的朋友圈推广文案，突出「本地优先、端到端加密、Markdown 原生」。
S（风格）: 极客、克制、不浮夸。
T（语气）: 自信但平实。
A（受众）: 重度 Markdown 用户、隐私敏感型开发者。
R（响应）: 只输出文案本身，不要任何解释。
```

模型真实输出（原样）：

```
DevNote：本地优先，端到端加密，Markdown原生，隐私无忧！🚀🚀🚀

我们是开发者必备的好帮手，专为程序员打造的云端笔记神器。本地化体验，端到端加密保护你的数据安全，支持Markdown原生编辑，让你轻松记录代码、想法和心得。告别繁琐手动输入，让每一次笔记都成为你专注力的最佳伴侣。🚀🚀🚀

加入我们，开启你的技术日记新纪元吧！🚀🚀🚀
```

## 真实解读：框架有用，但要迭代

对比"帮我写个产品文案"那种模糊提示词（模型直接反问你），CO-STAR 版**直接交付了文案、且覆盖了三个卖点**——框架价值明确。

但也暴露真实问题：

1. **超字数**：要求 60 字以内，实际给了三百字 + emoji。小模型遵循长度约束弱。
2. **语气偏移**：要求"克制不浮夸"，它给了"神器""最佳伴侣""新纪元"这种浮夸表达。
3. **自由发挥**：0.5B 模型本身指令遵循能力有限，换更大模型会好很多；真要硬控字数，得在应用层截断或加更强约束（"超出即无效"）。

**所以 CO-STAR 是起点不是终点**：跑完看输出，把没满足的点转成更硬的约束再迭代一版。

## 可直接复制的模板

```
# CO-STAR 提示词模板
C（上下文）: <背景/前置信息>
O（目标）:   <这次具体要做什么，可量化>
S（风格）:   <模仿对象/文风>
T（语气）:   <正式/轻松/自信/克制>
A（受众）:   <读者是谁>
R（响应）:   <格式/长度/禁忌，越硬越好>
```

适用场景：写 AI 应用的 system prompt、批量生成内容、给分类/抽取任务定规范。把 R 写死（比如"只输出 JSON，字段为..."）能大幅提升稳定性。

## 面试常考点

- **System vs User message**：CO-STAR 通常作为 system prompt 固化身份与规则，单次任务放 user。
- **为什么响应约束要硬**："只输出 JSON，不要解释"比"请尽量简洁"可控得多。
- **小模型 vs 大模型遵循力**：参数越小，指令遵循越弱；生产要权衡成本与可控性。
- **提示词版本管理**：好提示词要像代码一样迭代留存，记录每版改了什么、效果如何。

## 小结

CO-STAR 把"上下文/目标/风格/语气/受众/响应"六要素一次性钉死，比一句模糊需求强太多——本机真跑的对比就是证据。但它不是"填完就完美"：小模型会超字数、会语气漂移，框架解决方向，迭代解决落地。把 R 写硬、把模板当版本管理，才是能上生产的写法。
